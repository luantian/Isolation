一、数据正确性 / 可信度问题（核电场景最致命，建议最优先）
================================================================================

[1] 🔴 无真实过程数据时，自动伪造曲线当真实数据展示
    位置：TestRecordsViewModel.cs:981-1040 (GenerateSampleCurve)
          DatabaseInitializer.cs:465-538 (种子数据 Random 伪造)
    问题：选中记录查不到过程数据时，用随机数生成一条"像模像样"的压力/流量/
          温度曲线显示，界面无任何"模拟"标识。
    影响：工程师看曲线回放做泄漏率判断，把伪造曲线当真实采集，可能据此得出
          错误结论。数据可信度红线问题。
    方向：无数据时显示空状态"该记录无过程曲线"，绝不生成假数据。

[2] 🔴 文件匹配用双向子串包含，极易张冠李戴
    位置：DataUploadService.cs:286-322
    问题：项目/机组/对象匹配用 Code.Contains(folder) || folder.Contains(Code)。
          机组"1"会命中"11""21""机组1号"。
    影响：数据被静默挂到错误的项目/机组/阀门上，界面还显示"✅就绪"，用户无感知，
          污染历史与统计。
    方向：优先精确匹配；模糊命中多个候选时标记"歧义需人工确认"，而不是取
          FirstOrDefault。

[3] 🔴 批量上传无法纠正"未匹配"项，且"批量设置"会误操作
    位置：BatchUploadView.xaml（未绑定命令）
          BatchUploadViewModel.cs:378-427 (ExecuteSetProjectForSelected 等)
    问题：XAML 根本没绑定 SetProjectForSelected 等命令，DataGrid 也无选中/复选。
          界面显示"待补充 N 个"，但用户没有任何入口去补全。即使接上，逻辑是
          "应用到所有未匹配项"，会把分属不同项目的文件错配到同一项目。
    影响：未匹配文件无法补救；批量设置会造成数据错配。
    方向：DataGrid 加多选 + 行内下拉纠正，命令作用于真正选中行。

[4] 🔴 编辑路径节点先改内存再存库，存库失败造成界面与数据库不一致
    位置：TestObjectPathManagementViewModel.cs:776-808 (EditSelectedNodeAsync)
    问题：先就地改 SelectedNode 并刷新 UI，之后才 SaveChangesAsync。失败时界面
          显示新值、数据库仍是旧值。
    影响：泄漏率限值这类关键参数，用户以为改成功了，实际没入库，下次刷新又变回去。
    方向：先保存成功再更新内存，或失败时回滚。

[5] 🟠 重复检测只查最近 1000 条，老对象会漏判
    位置：DataUploadService.cs:594 (GetByObjectAsync(objectCode, 1000))
    问题：取该对象最近 1000 条记录后在内存比时间。试验频繁的阀门超过 1000 条后，
          更早的同时刻记录查不到，可被重复入库。
    方向：改成数据库侧 AnyAsync(ObjectCode==x && TestTime BETWEEN ...)。

[6] 🟠 按"系统"统计漏算挂在贯穿件下的阀门
    位置：StatisticsAnalysisViewModel.cs:776-781
    问题：条件是 Parent.Code == SystemCode，只统计直接挂系统下的对象。但业务层级是
          系统→贯穿件→阀门，挂在贯穿件下的阀门会被漏掉。
    影响：按系统统计数据偏少且不自知，统计结论失真。
    方向：递归包含该系统下所有子孙对象，或预存对象所属系统编码。

二、验收阻断 / 需求缺失

[7] 🔴 任务下载实际跑不通（阻断级）
    位置：TaskDownloadViewModel.cs:248-303 (CreateTaskAsync)
          SerialConnection.cs:109-148（串口帧格式 TODO 占位）
    问题：直接调下载，从不先连接装置，界面也无"连接装置"按钮。GetConnection 未连接
          时返回 null → 必抛"设备未连接"。当前接线下任务下载必然失败。串口帧格式
          仍是 TODO 占位。
    影响：7.7 任务下载需求当前不可用。

[8] 🔴 权限仅靠菜单隐藏，缺方法级强制拦截（违反 11.3）
    位置：用户/角色/菜单管理 ViewModel（无 Require/HasPermission）
          MainViewModel.cs:225-246（仅隐藏菜单）
          TestObjectPathManagementViewModel.cs:69（删除借用 PathAdd 权限）
          TestRecordsViewModel.cs:495（删除记录借用 records:data:upload 权限）
    问题：用户/角色/菜单管理无任何权限校验，仅靠隐藏菜单。备份/恢复/迁移有方法级
          Require（合规）。路径删除、删除试验记录借用了其他权限，无独立删除权限。
    影响：权限可被绕过；无法做"能建不能删"等精细控制。

[9] 🔴 三类核心操作零审计日志（违反 7.16）
    位置：任务下载、数据上传、报告导出（均无写日志）
          OperationLogViewModel.cs:35-36（登录/登出查不到）
          UserSession.cs:90 (Logout 全项目无调用点)
    问题：任务下载、数据上传、报告导出完全无操作日志——7.16 明确点名要求。
          登录/登出写入独立 LoginLogs 表，不进 OperationLogs，导致操作日志页选
          "登录/登出"永远查不到。登出动作无任何记录。
    影响：审计追溯不完整，验收会被质疑。

[10] 🔴 自动备份名不副实
    位置：SystemManagementViewModel.cs:330-347 (DispatcherTimer)
    问题：用进程内 DispatcherTimer，程序关闭即停，下次开机重新计时。现场常态是用完
          关程序，"每天自动备份"可能很久没跑过一次。备份目录/保留天数 UI 只读，
          只能改 JSON。
    影响：数据丢失风险被低估。
    方向：基于"上次备份时间"墙钟判断 + 启动补备，或用 Windows 计划任务。

[11] 🟠 第(6)类分析"不同类型阀门泄漏率曲线"完全未实现（7.12）
    问题：无对应视图/方法。另：
          - 第(2)单阀门试验次数、第(4)整机组合格情况：只有表格无图表
          - 第(5)单阀门泄漏率趋势：把所有阀门混成一条曲线、X 轴非时间、
            无阀门选择器，语义错误
          - 第(1)故障类型趋势：是静态分布堆叠条形，无时间趋势维度
          - 第(8)不合格标识：仅对象级色块，无记录级下钻追溯

[12] 🟠 部分需求功能前端断链或字段缺失
    - 项目/机组的修改/删除/停用 UI 缺失（后端 Service 有能力，ViewModel 未暴露命令）；
      归档状态未实现（EnabledStatus 只有 Disabled/Enabled）。(7.2)
    - 无独立"阀门及部件管理"台账页（7.4）；贯穿件限值与阀门限值合并成单一
      LeakageLimit 字段（TestObjectPathNode.cs:71），无法同时承载两类限值。
    - 数据查询缺 系统/贯穿件/阀门类型/操作人 筛选项（7.11）；试验记录与导出缺
      "系统"列。
    - 装置在线状态运行时不刷新（StartHeartbeat/ConnectDeviceAsync 无调用方）；

三、性能问题
================================================================================

[13] 🔴 进程级单例 DbContext 被上传热路径共享
    位置：AppServices.cs:38-63
          TestRecordService.cs:13-18、DataUploadService.cs:87,115,121,173,193
    问题：整个应用生命周期一个 AppDbContext 不释放，且是跟踪查询无 AsNoTracking。
          ① ChangeTracker 累积实体，内存只增不减（核电要求长期驻留）；
          ② 线程不安全，后台实时线程 + UI 命令同时命中会抛异常或数据损坏。
          其余 ViewModel 已改用 DbContextFactory（正确），唯独上传热路径没改。
    方向：让 TestRecordService/DataUploadService 也用 DbContextFactory.CreateDbContext()
          创建短生命周期 context（参考 RecipeService.cs:18 的写法）。

[14] 🔴 统计页用 Task.WhenAll 在同一 context 并行跑 5 个查询
    位置：StatisticsAnalysisViewModel.cs:557-569
    问题：EF Core 禁止同 context 并发，会抛"A second operation was started on this
          context"。TestObjectPathManagementViewModel.cs:418 注释已经知道这个坑。
          每个子查询还带 4 个 Include（聚合查询不需要）。
    方向：顺序 await，或每查询独立 context；聚合查询去掉不必要的 Include。

[15] 🔴 批量上传 N+1 放大 + 内存过滤
    位置：DataUploadService.cs:379-432 (BatchUploadAsync)、588-603 (CheckDuplicateAsync)
    问题：N 个文件 = N 个事务 + 约 5N 次往返 + N 次"拉 1000 条到内存"。上千文件
          会非常慢。每条还重复查配方/节点/版本。
    方向：批量前预加载配方/节点字典，去重下推到 SQL（AnyAsync），单事务 AddRange。

[16] 🟠 其它中等性能问题
    - GenerateUniqueCodeAsync 每次新建节点全表 ToListAsync
      (TestObjectPathManagementViewModel.cs:971-993)
    - 递归 CheckNodeAndDescendantsHaveRecordsAsync 逐层往返数据库，选中节点即触发
      (TestObjectPathManagementViewModel.cs:503-524)
    - 大量 ICommand 属性写成 => new RelayCommand(...)，每次绑定刷新都新建实例
      (TestObjectPathManagementViewModel.cs:316,319；TestRecordsViewModel.cs 多处；
       RecipeManagementViewModel.cs 11 处)——CanExecute 失效 + GC 抖动
    - 导出全量加载带 Include 整实体 (TestObjectPathManagementViewModel.cs:1189-1195)
    - BuildSummarySheetData 用同步 Count() 阻塞 (StatisticsAnalysisViewModel.cs:403-417)
    - BatchUploadViewModel 逐条 Add 触发 O(N²) 统计重算 (BatchUploadViewModel.cs:39,255)

[17] 🟡 索引相关
    - TestRecords.Result 无索引，但概览页和统计页大量按 Result==Pass/Fail 计数
      (OverviewViewModel.cs:253-254)。数据量大后会扫描。建议 (Result, TestTime) 索引。
    - 模型快照有 DeviceCode1 影子外键列 (AppDbContextModelSnapshot.cs:923)，说明
      TaskDownloadRecord 与装置的关系未配好，多一列 + 多一索引。
    - 关键词搜索 LIKE '%kw%' 前导通配符无法走索引 (TestRecordsViewModel.cs:722)。
    - DataGrid 未显式启用虚拟化 (Styles/IndustrialTheme.xaml:486-509)，当前分页
      PageSize=10 风险低，建议显式声明防回归。
    【索引整体良好】TestRecords 上 ObjectCode/TestTime/UnitCode/复合索引齐全；
    TestProcessData 以 RecordCode 为主键、大 JSON 字段隔离独立表，设计合理。

四、交互体验问题
================================================================================

[18] 🟠 给用户看的错误里塞技术堆栈和表名
    位置：TestRecordsViewModel.cs:619,677 (ErrorDetail 含 ex.StackTrace 并可复制)
    问题：查询失败把异常类型、消息、完整 StackTrace 显示给用户。现场工程师看不懂
          还暴露内部表名。
    方向：界面只显示友好中文，堆栈写日志文件。

[19] 🟠 重要错误消息 3 秒自动消失
    位置：TestObjectPathManagementViewModel.cs:218-241 (SetMessage 固定 Task.Delay(3000))
    问题：所有提示（含错误）统一 3 秒清除，"已有历史记录不允许删除""创建失败"
          一晃而过。
    方向：错误/警告类不自动消失或延长到 8-10 秒，仅成功提示短暂显示。

[20] 🟠 危险删除提示顺序颠倒
    位置：TestObjectPathManagementViewModel.cs:821-864
    问题：先弹"不可恢复"确认，点 OK 后才查能不能删，查到不能删再拒。
    方向：不可删时直接禁用删除按钮（已有 DeleteButtonToolTip 解释原因）。

[21] 🟠 删除确认用 OK/Cancel，默认焦点 OK，回车即删
    位置：TestObjectPathManagementViewModel.cs:824、TestRecordsViewModel.cs:521
    方向：统一用 YesNo 且默认 No；删除类可要求输入对象编码二次确认。

[22] 🟠 配方参数无数值校验，0/负值/空都能保存
    位置：RecipeManagementViewModel.cs:132-147 (Validate 只查编码和名称非空)
          DataUploadService.cs:122（NormalExpectedLeakFlow 当判定限值用）
          RecipeService.cs:419（默认配方 A/B/C 的 NormalExpectedLeakFlow 初始为 0）
    问题：压力、限值等十余个参数无范围校验，限值为 0 会导致判定失真。
    方向：关键参数加 >0 及合理上限校验。

[23] 🟠 配方删除提示与实际行为不符
    位置：RecipeManagementViewModel.cs:337-356、RecipeService.cs:189-211
    问题：确认框说"有记录则仅禁用"，但无论软删硬删都统一弹"操作成功"，用户不知道
          到底删没删。版本历史只是 MessageBox 拼字符串，无 diff 无回滚。
    方向：根据实际结果分别提示"已删除"或"被 N 条记录引用，已禁用"。

[24] 🟠 统计页打开默认空白，需手动点"应用筛选"
    位置：StatisticsAnalysisViewModel.cs:270-273
    问题：进入页面所有图表/数字都是空，用户以为没数据或坏了。
    方向：进入页面默认按"全部/近 30 天"自动出一版数据。

[25] 🟠 数据库还原/导入后程序继续用旧缓存运行，不重载
    位置：SystemManagementViewModel.cs:530-592（还原）、644-706（导入）
    问题：还原/导入成功后程序不重启、不刷新，各页面缓存仍是旧的，显示新旧混杂。
    方向：成功后强制重启应用或全局刷新所有 IRefreshable 并清缓存。

[26] 🟠 任务下发部分失败无明细、无重试，过程不禁用按钮可重复点
    位置：TaskDownloadViewModel.cs:248-303
    方向：下发结果弹明细（成功/失败对象清单）+ 失败项重试；执行期间禁用命令。

[27] 🟠 大量静默 catch 吞掉失败
    位置：DataUploadViewModel.cs:307-310、BatchUploadViewModel.cs:308-311、
          PathNodeEditorDialog.xaml.cs:245-248、StatisticsAnalysisViewModel.cs:309-312、
          SystemManagementViewModel.cs:294-297,472-475 等
    问题：配方/备份/筛选项加载失败 catch {}，用户分不清"加载失败"还是"暂无数据"。
    方向：失败至少给可见提示或区分空状态文案。

[28] 🟡 其它体验细节
    - 单文件上传关键字段等到入库才报错，且不校验编码是否真实存在

    - 配方选择三态语义（null=默认/0=不用/正数=指定）对用户不可见且易混

    - 批量上传不可中断、失败项无法单独重试 (DataUploadService.cs:379-432)

    - 筛选条件触发时机不一致：下拉/日期即时查询，搜索框要点按钮

五、整体判断与建议修复顺序
================================================================================

核心数据链路（解析→匹配→入库→判定→统计）已跑通，工程化程度不低（删除保护、
配方快照、分页、事务一致性都做了）。但最该先修的是会导致数据错挂或数据不可信的
几处——在核电台账场景下这些比交互顺手与否严重得多。

建议修复顺序：

    [10] 自动备份名不副实

第三批（需求缺失 + 性能优化）：
    [5][6][11][12][15][16][17]

第四批（交互体验打磨）：
    [18]~[28]

6.1 甲方明确要求但代码完全缺失的功能
--------------------------------------------------------------------------------

[29] 🔴 双服务器主备 + 主从同步 + 故障切换 完全未实现（甲方硬性要求）
    依据：技术规格书 PDF 第 14 节"数据管理软件：配置双服务器，主备同时运行。
          配置笔记本电脑，用于服务器管理和数据库管理。"
          哈工程设计方案：3.3"主备服务器间实现数据库实时同步（主从复制），主服务器
          故障时可快速切换至备用服务器"；联调要求"模拟主数据库故障，验证自动切换
          时间≤5分钟"。
    核实：grep 主备/主从/双服务器/standby/failover/replication 全代码库零命中。
    现状：单机 WPF + 本地 SQL Server Express，无任何主备/同步/切换架构。
    影响：这是甲方写进规格书和验收联调的硬指标，当前架构层面缺失，验收风险极高。
          "数据库同步迁移"现有实现（SQL 脚本导入导出）≠ 主备实时同步。
    方向：需与甲方确认验收口径。若必须满足，应上 SQL Server 标准版的
          AlwaysOn/镜像/日志传送或主从复制，并提供故障切换演练；当前 Express 版
          不支持部分高可用特性，可能需调整数据库选型。

[30] 🔴 真实装置数据格式（西门子 PLC 5 通道）与代码解析格式不匹配
    依据：doc/以太网通讯设备-数据地址.xlsx —— 真实装置是西门子 1211C PLC
          (IP 192.168.1.12)，5 个通道：压力P1(MD512 Real)、流量M1(MW804 Uint)、
          流量M2(MW806 Uint)、温度T(MD500 Real)、压力P2(MD504 Real)。
          doc/数据导出格式.csv 表头同样是 5 列：实时压力P1/瞬时流量M1/瞬时流量M2/
          温度T_R/压力P2_R。
    核实：DataUploadService.ParseTextAsync:477-541 只解析键值对 + 单一 ProcessData
          JSON（Time/Pressure/Flow/Temp 四字段），无 CSV 表头解析、无 P2、无 M1/M2
          双流量通道。TestProcessData.cs 模型只有 Pressure/Flow/Temp 三条曲线，
          缺 P2（第二压力）、缺 M1/M2 区分（高/低量程流量）。
    影响：装置实际产出的 CSV（5 通道）无法被正确解析入库，P2 和双流量通道数据丢失。
          阶段一"数据包解析逻辑"实为未对接真实格式。
    方向：按真实 CSV 表头解析（含 P2、M1、M2），过程数据模型扩展到 5 通道。

[31] 🔴 PLC 以太网通讯未对接（真实装置走 RJ45/Modbus，非 U盘）
    依据：装置含 PLC 控制器"支持串行通信和以太网通信"，地址表是以太网 PLC 寄存器。
          甲方规格书装置预留 USB / RJ45 网络 / RS232/485 多种接口。
    核实：SerialConnection.cs 串口帧 TODO 占位；无 Modbus/TCP 读 PLC 寄存器实现。
          我方"阶段性功能列表"称已移除 PLC（"不在客户需求范围内"）——但装置本身就是
          PLC，数据地址表是甲方提供的，PLC 以太网读数恰恰是真实取数通道。
    影响：我方文档对"PLC 不在范围"的判断与甲方实际装置/数据地址表矛盾，可能误判范围。
    方向：与甲方确认数据交付方式（U盘导出 CSV vs 以太网实时读 PLC）。若走以太网，
          需实现 Modbus-TCP/S7 协议读 MD512/MW804 等寄存器。

[32] 🟠 湿度数据未存储（甲方多次提到湿度传感器与多因素研究）
    依据：规格书"扩展采集试验对象中湿度""验证多环境因素耦合对试验结果的影响"；
          数据分析"可叠加温度、湿度影响曲线""多因素拓展研究"。
    核实：grep humidity/湿度 全代码库零命中；TestProcessData 无湿度曲线字段。
    影响：甲方强调的"多因素（含湿度）对密封性影响研究"缺数据支撑。
    方向：过程数据模型增加湿度通道，解析与曲线展示同步支持。

[33] 🟠 过程数据丢弃采集时间，与哈工程自家设计方案矛盾
    依据：哈工程设计方案 3.1 明确 test_data_details 表设计含
          timestamp_offset（相对测试开始的时间偏移）字段。
    核实：TestProcessData.cs 只存 PressureCurveJson 等 double[] 数组，无时间轴；
          BuildProcessData 丢弃 Time，X 轴退化为采样序号。
    影响：违背"按采集时间顺序展示过程数据"（规格书）和自家设计方案；采样间隔不均匀
          时曲线时间轴失真。
    方向：过程数据保存时间偏移序列，X 轴用真实时间。

四、甲方会问的专业问题 + 应对话术
================================================================================
按"几乎一定会问"到"可能会问"排序。
【主打真实技术点】= 代码里真做到了，可以硬气地答。
【诚实边界】= 别吹过头，被一查就露的地方。

--------------------------------------------------------------------------------
A. 数据完整性与不可篡改（核电最核心，必问）
--------------------------------------------------------------------------------

Q：怎么保证同一试验对象多次上传不覆盖历史数据？
答：上传只做 INSERT，没有任何 UPDATE/覆盖逻辑；每条记录有唯一记录编号
   （项目_机组_对象_时间戳）。同一对象再次试验就是新增一条历史记录，
   按时间排序存储。这是规格书 13.3 和不可篡改要求的硬指标，
   我们从数据层就杜绝了覆盖。

Q：上传中途失败会不会产生半截的脏数据？
答：主记录 + 5 通道过程数据的写入用【数据库事务】包裹，要么全成功要么全回滚，
   不会出现主记录有、过程数据缺的不一致情况。

Q：怎么防止重复上传同一份数据？
答：有重复检测：相同试验对象 + 相同试验时间会被识别为重复并提示。
   （诚实补充：这块正在把检测从内存比对优化为数据库侧查询，保证大数据量下
   也准确——主动说反而显专业）

--------------------------------------------------------------------------------
B. 与测量装置的数据对接（必问，核心）
--------------------------------------------------------------------------------

Q：软件怎么和装置交换数据？支持什么格式？
答：装置一次试验导出曲线 CSV（实时压力P1、瞬时流量M1/M2、温度、压力P2 五通道
   时序数据）+ 结果汇总文件。软件按文件夹层级（项目/机组/对象）自动匹配台账，
   解析 5 通道曲线和判定结果入库。【泄漏率和合格判定由装置算好，软件只读取保存，
   不参与计算】——符合规格书里软件不做泄漏率计算模型的边界。

Q：实时通讯（RS232/485/网络）什么时候能用？
答：通讯框架（串口/网络/U盘）已搭好。实时读取装置数据这块，我们看到装置是
   西门子 1211C PLC、以太网，【需要贵方确认走 Modbus 还是 S7 协议、提供寄存器
   映射和字节序】，确认后即可联调。这是规格书里"接口设计阶段进一步确认"的部分。
   💡 把球合理地踢回甲方——他们确实还没给协议文档，这是真实依赖，不是你的锅。

--------------------------------------------------------------------------------
C. 高可用 / 双服务器主备（高风险，大概率被问）⚠️ 必背
--------------------------------------------------------------------------------

Q：规格书要求配置双服务器主备同时运行，主库故障 5 分钟内切换，这块怎么实现？

答：当前交付的是单机版本，完整跑通了数据管理的全部业务链路。双服务器主备属于
   【部署架构层】，我们的方案是用 SQL Server 的 AlwaysOn 可用性组（或数据库镜像/
   日志传送）实现主从实时同步和自动故障切换，这部分依赖贵方现场的服务器环境和
   网络确认后部署落地。【需要和贵方对齐：现场是两台物理服务器还是虚拟化？
   数据库版本能否用支持 AlwaysOn 的标准版？】这会影响主备方案的具体落地方式。

⚠️ 重要自知：你现在用的是 SQL Server Express 版，它【不支持 AlwaysOn】。
   如果甲方追问版本，诚实说"生产部署会升级到标准版以支持高可用"，
   别承诺 Express 能做主备。

--------------------------------------------------------------------------------
D. 权限与安全（会问）
--------------------------------------------------------------------------------

Q：不同角色权限怎么控制？普通用户能不能误删数据、做备份恢复？
答：基于角色的权限控制（RBAC），按菜单和操作分配权限。备份、恢复、数据库迁移
   这类高危操作有【方法级强制拦截】，普通用户执行会被直接拒绝。
   💡 诚实边界：用户/角色管理这些页面目前只靠隐藏菜单、没有方法级拦截。
   若深问"每个操作都拦截吗"，说"高危的备份恢复迁移已强拦截，其余操作权限边界
   正在逐项加固"。别吹成全覆盖。

Q：防 SQL 注入怎么做的？
答：全部用参数化查询，不拼接 SQL。

Q：密码怎么存的？
答：BCrypt 加盐哈希，不可逆、不存明文。

--------------------------------------------------------------------------------
E. 数据量与性能（可能问）
--------------------------------------------------------------------------------

Q：历史数据积累很大后查询会不会慢？
答：试验记录表在试验对象编码、试验时间、机组等字段建了索引，含复合索引，
   支撑按对象和时间范围查询；列表分页加载。过程数据（大字段）单独存表、
   按需加载，不拖累主查询。

--------------------------------------------------------------------------------
F. 审计追溯（可能问）
--------------------------------------------------------------------------------

Q：关键操作能不能追溯到人？
答：台账增删改、备份恢复、导出等操作记录操作日志，可按时间/用户/类型查询。
   💡 诚实边界：数据上传、任务下载这两类目前还没记日志。
   若被问到上传有没有日志，说"上传入库的审计日志我们正在补全"——
   别说已经全有了，甲方一查就露。

--------------------------------------------------------------------------------
G. 数据库选型（如果他们看过哈工程那版设计方案，会问）⚠️
--------------------------------------------------------------------------------

Q：设计方案里写的是 MySQL + Linux，怎么实际用的是 SQL Server + Windows？

答："早期方案探讨过 Web 混合架构，后续综合考虑现场是 Windows 环境、要和装置做
   串口/USB 原生通讯、以及部署运维的简便性，最终确定为 WPF + SQL Server 的原生
   桌面架构，稳定性和硬件对接能力更适合现场。我们会同步更新设计方案文档与实物一致。"

⚠️ 演示前务必确认：你交给甲方的是哪一版设计方案？
   如果交的是 MySQL/Linux 那版（哈工程 V1.1），赶紧准备好这套说辞，
   否则现场对不上很尴尬。
